## 目标

判断 **openpipal 的编码助手能不能当日常主力**。

这句话是判据，不是口号。它意味着：

- 要测的是"接一个真实任务，它能不能自己做完并且不打坏别的地方"，
  **不是**在某个公开榜单上拿多少分。绝对分和官方榜单不可比（环境不是官方镜像），这是明写的取舍。
- 所以加任何一个新样本之前先问：**这个样本回答的是不是这个问题。**
  能刷高分但不像日常工作的题，不要。

评测台有两套，服务同一个目标的不同侧面：

| | 题库 | 测什么 | 目录 | 状态 |
|---|---|---|---|---|
| SWE-bench | 官方 253 道 Python 题 | 干净的 Python bug 修复 | `$BENCH_SCRATCH`，默认 `~/openpipal-bench/swebench` | scratch 空着，没重建；影子运行已不依赖它 |
| **影子运行** | **openpipal 自己的历史提交** | **TypeScript、双 tsc 类型检查、全量单测不回归** | `$SHADOW_SCRATCH`，默认 `~/openpipal-bench/shadow` | **在用** |

**重心是影子运行**，因为这个项目的日常是 TypeScript + 双 tsconfig + 主/渲染进程边界，
SWE-bench 一行都没测到。判据三条缺一不可：F2P 测试由红转绿 / 全量单测不回归 / 双 tsc 不新增类型错。

背景细节在 `tests/bench/README.md` 和 `tests/bench/shadow_prep.py` 的文件头，用到再读。

### 25% 为什么是低估：判据绑住了作者的实现选择

这批题都过了现有三道闸（题面不含答案标识符 / 文档不泄题 / 判据不绑题面推不出的东西），
测试本身也合理。问题更隐蔽：**隐藏测试把"作者选的那种写法"当成了唯一正确答案，等价的另一种写法判 0。**
逐条读模型的 `patch` 对着 `.test.patch` 看出来四类，每类都有实证：

1. **绑形状**（`cf568f443`）——测试 `toEqual` 一个字面量对象 `{ minimal: null, medium: null, xhigh: null, max: 'max' }`。
   模型写的是 `{ medium: 'high' }`，靠 pi 自己 clamp 掉不认的档位；诊断和注释跟标准答案几乎一字不差，只是编码方式不同。两种都能用。
2. **绑缝**（`f62d540b0`）——测试 import 的是 `classifyToolRisk`。模型轮 3 把门闩装在 `createSecurityHook`
   （真正执行拦截、返回 `block: true` 的地方），测试永远走不到那儿。运行时防护比轮 2 更强，得分 0 对 2。
3. **绑措辞**（`b9646d8`）——`expect(reason).toContain('删除')`，要模型猜中人读的提示语里用哪个词。
4. **绑环境**（`0ad87edaf`）——测试在没有 Electron 的单测环境里 mock `process.resourcesPath`；
   模型三轮都按 `app.isPackaged` 判（正式版里这是对的，**题面自己还写着"只在正式版里有"**），单测里 `isPackaged` 永远是 false，门闩从不触发。

这和 `dropped-tasks.json` 里那两道不一样：那两道是"要猜中作者起的名字"，现有第 ③ 道闸查得出；
这四类是"代码能用但写法不同"，**现有闸门查不出，第五道闸还没建**（要做什么见「重启时按这个顺序做」）。

### 对「能不能当日常主力」的回答

- **没有粗大缺陷。** 类型安全、不破坏、定位准——这三点是评测台最擅长抓的，都抓过了。
- **两个真短板**，等反馈时盯这两类：
  - "修在表面没修到根"——`f08393e3c` 要把两个判断来源并成一个，三轮都只修了一半。
  - "修了 X 打坏了 Y"——`6919551` 是并发/状态机改动，两轮打坏 4 条老测试（连接就绪判定、ping 往返、宽限期重连、错误 reject）。
- **评测台测不到的**：多轮协作、提问质量、长会话不迷路。这些恰恰是"日常主力"的核心，只有真用才知道。

**为什么停：** n=8 加上判据有噪音，做不了任何 A/B；眼下也没有待验证的提示词/模型改动需要挡板；
真实反馈出的题比 git 历史好——题面是用户原话，判据是"问题解决了没"，不是"跟作者 diff 一致"。

**别先改提示词。** 编码角色提示词很小（`coding-role.ts` 约 1.2k token + `openpipal-prompt-core.ts` 约 3k token，按字符/4 估），
往里加题目特定的提示来抬分，是对着答案过拟合——按机制分层的判定公式，那是能力拐杖，不是架构。

### 重启触发条件

- 用户反馈里出现上面两类之一 → 把它写成题（用户原话当题面，"问题解决了没"当判据），这是最好的新题来源。
- 有提示词 / 模型 / 工具集的改动需要对照 → 先把下面的顺序走完再 A/B。

### 重启时按这个顺序做

1. **建第五道闸**（放 `shadow_leakcheck.py`），对着每道题的 `.test.patch` 查四类：
   `toEqual` 一个有等价编码的字面量结构 / 只认一个函数缝 / 断言人读文案里的中文 / 只在非 Electron 单测环境里才不同的行为。
   前三类脚本能查，第四类要人看。
2. 重扫 `tasks.json` 21 道，看剩几道。
3. 重跑剩下的题拿一条干净基线。**那时的数字才配拿来和改提示词做对照。**
4. 语料往两位数扩，挑题回到「目标」那节的判据：像不像日常工作。

## 别踩的坑

1. **`build ≠ 类型检查`**——项目红线。改了签名必须跑双 tsc（`tsconfig.node.json` 和 `tsconfig.web.json`）。
2. **`thinSuite=true` 的题，"不回归"这条判据形同虚设**——那些快照只有 70 条单测。目前 `6919551` 是这一类。
3. **单轮结果不可信，至少三轮。** 同一道题在同样代码下会翻面（`f62d540b0` 三轮 0/3、2/3、0/3）。
4. **跑批耗时不能跨轮比。** 判分靠跑测试不看墙钟，但耗时那一列被机器负载左右（同样的题 6 分变 13 分）。
5. **凭据不对 AI 开放。** 清单见 `src/main/credential-paths.ts`，需要看的让用户自己在终端跑。
6. **别用宽泛的 `pkill` 清 Electron 进程**——只杀自己记下来的 PID，全局 pkill 打掉过用户正在跑的真机验证。
7. **"解决率"不能直接读。** 先翻 `patch` 对 `.test.patch`，分清是模型没做到，还是判据绑了作者的写法。这批 5 道没全过的题里至少 3 道是后者。
8. **`confirm_regress` 别拆。** 拆了会稳定地把对的判成错的。
