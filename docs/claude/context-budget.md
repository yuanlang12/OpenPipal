# Context Budget 设计原则

**上下文空间是最宝贵的资源。既不要无意义地占满，也不要随意地清空。**

## 原则一：按需获取，不主动注入

所有信息获取都应该由 AI 主动决定是否需要，提供工具/能力让 AI 自己判断。

1. **不主动注入大段内容到上下文**。页面正文、视频字幕、文档内容等应作为工具提供，让 AI 判断是否需要获取，而非每次对话都塞进 system prompt 或用户消息。
2. **工具描述要精简**。当工具数量多到占上下文 >10% 时，应使用 tool_search 模式（类似 Claude Code 的做法），AI 先搜索再加载具体工具 schema。
3. **Skills 按需加载**。只在 system prompt 中注入技能索引（名称+一句话描述+位置），完整内容由 AI 用通用 `read` 工具按需加载（Stage 2 Unix 化后已无专用 load_skill 工具，见 role-manager.ts 注释）。
4. **记忆注入要克制**。只注入最近 N 条摘要（而非全部历史），详细内容由 AI 用通用 read/grep 按需获取（save_memory/recall_memory 专用工具已删除，记忆即 `~/.openpipal/memory/` 下的文件）。
5. **关注 KV Cache 命中率**。system prompt 和工具定义应尽量稳定不变（放在消息序列前部），动态内容放后部，以最大化 KV Cache 复用（参考 Manus 团队的实践）。
6. **不要在提示词里教 AI 选工具**。把工具描述写清楚就够了，规则越多上下文越臃肿，AI 反而更容易被干扰。

反面案例：把视频字幕直接拼到用户消息里 → 每轮对话都带上 8000 字字幕 → 浪费 token 且可能与用户问题无关。
正面案例：提供 `read_page_content` 工具 → AI 判断需要时才调用 → 只在相关时占用上下文。

## 原则二：对话连续性 vs 环境动态性

对话历史和页面环境是**两个独立的生命周期**，不要混淆。

- **对话历史是连续的**：只有用户主动清空或超出上下文窗口才重置。切换 tab、切换页面、切换应用都不应该清空对话。用户可能在 A 页面查信息，切到 B 页面继续讨论，对话上下文不能丢。
- **页面环境是动态的**：跟随当前 tab/应用实时变化。AI 通过工具（`read_page_content`/`capture_screenshot`/`read_screen`）按需读取当前环境，每次调用拿到的是最新状态。
- **只注入轻量提示**：当前页面标题、选中文本等极小的提示可以注入用户消息（帮 AI 判断是否需要调工具），但大段正文/字幕不注入。

## 原则三：优先集成，不重复造轮子

新增能力时先看有没有现成的 MCP server 或 Skills 可用，而非自己实现。同样适用于工具（如 Context7 查文档、DeepWiki 查仓库），也适用于页面内容提取（参考 read-frog 等开源项目的方法，但注意授权协议）。
